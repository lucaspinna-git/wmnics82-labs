8.1 Database Basics & Data Integrity

Explore why modern IT systems store critical data in dedicated database management systems rather than spreadsheets. Master the CRUD operational lifecycle, contrast record locking against file collisions, and understand local, network, and cloud database access architectures.

8.1.1 What is a Database? (The CRUD Lifecycle)

Core Definition
🗄️

Definition & Purpose

CompTIA Tech+ Section 9.1.1

A database is an organised, structured collection of digital information stored electronically in a computer system. Unlike a static text file or printed ledger, a database is governed by a Database Management System (DBMS) — specialised software that manages how data is stored, indexed, secured, backed up, and retrieved by multiple users simultaneously.

Key Invariant: Data is stored centrally so that multiple applications, staff members, and web portals query one authoritative source of truth.

⚡ The 4 Essential Operations (CRUD)

Vocational Foundation
C • CREATE Adding a new record (e.g. enrolling an apprentice or registering a customer).
R • READ Querying and viewing records (e.g. searching an inventory catalogue by product code).
U • UPDATE Modifying existing values (e.g. updating an employee mobile number or stock count).
D • DELETE Removing or archiving unneeded records (e.g. cancelling a duplicate order).
⚠️ Level 1 Exam Trap: Database vs DBMS

Do not confuse the Database with the DBMS. The database is the passive collection of data records (the digital filing cabinet). The DBMS (Database Management System) is the active software engine — such as MySQL, Microsoft SQL Server, PostgreSQL, or Microsoft Access — that executes queries, validates data types, enforces permissions, and prevents simultaneous write collisions.

📜 History Bite: 1970 & The Magnetic Tape Bottleneck

Before 1970, enterprise data lived on sequential magnetic tape reels. Updating record #50 meant rewinding the entire tape and rewriting every record sequentially onto a new spool! In 1970, IBM mathematician Dr Edgar F. Codd published his landmark paper introducing the Relational Model — organising data into independent tables linked by unique keys, allowing instant direct indexing without scanning physical tapes.

8.1.2 Vocational Scenario: The Seaside Ice Cream Parlour

Lesson 8 Slide 9 • Why Paper & Standalone Spreadsheets Break Down
Slide Context
The Business Requirement:

The shop operates 3 till terminals. Staff must track daily cone sales, 16 ice cream flavours (Vanilla, Mint Choc Chip, Salted Caramel), customer loyalty card points, and dairy supplier deliveries.

The Spreadsheet Failure:

If Till 1 and Till 2 both open the same spreadsheet file to log a scoop of Salted Caramel simultaneously, the second till receives an error message: "File Locked for Editing by Till 1"!

The Database Solution:

A relational DBMS allows all 3 tills and the back-office manager to query and update stock in real time using row-level locking, preventing data corruption and lost revenue.

8.1.3 Database vs. Spreadsheet: Comprehensive Vocational Matrix

CompTIA Tech+ 9.1.4

Spreadsheets are fantastic personal productivity tools for ad-hoc mathematical calculations, charts, and financial models. However, when an organisation needs multi-user operational reliability, a database is mandatory.

Feature / Capability Flat Spreadsheet (Excel / Google Sheets) Relational Database (SQL / Access / PostgreSQL) Vocational Significance
Data Capacity & Scale Slows dramatically after 50,000–100,000 rows. Limited strictly by local workstation RAM. Scales effortlessly to millions or billions of rows across distributed disk storage arrays. Large enterprise datasets crash spreadsheets upon opening.
Multi-User Concurrency Entire file locking or messy merge collisions when multiple staff edit identical cells. Granular row-level locking: thousands of staff read and write simultaneously without conflicts. Enables call centres, web shops, and checkouts to operate simultaneously.
Relational Data Linking Fragile VLOOKUP / XLOOKUP formulas that break if rows are sorted or renamed. Native Primary and Foreign Keys enforce strict, permanent relational links between tables. Guarantees an order always links to a valid existing customer.
Data Redundancy High redundancy: Customer addresses re-typed repeatedly in every row, causing typos. Normalisation: Customer details stored exactly once in tbl_customers and linked. Updating a customer address once updates all past and future orders automatically.
Security & Permissions All-or-nothing file password. Anyone with access can read executive salaries or customer emails. Role-Based Access Control (RBAC): Restrict permissions by table, column, row, or user role. Strict compliance with UK GDPR and Data Protection Act 2018.
Data Validation Rules Weak: A user can type text into a price column, breaking financial totals. Strict data types (INT, DECIMAL, DATE, VARCHAR) reject invalid input at the engine level. Prevents corrupted accounting records from ever entering the system.
💡 Technician Top Tip: The 4-Point Decision Rule

When advising a business client whether to keep using Microsoft Excel or upgrade to a database management system, apply this straightforward vocational rule:

1. Concurrency If >1 person needs to write data simultaneously → DBMS
2. Volume If records exceed 50,000–100,000 rows → DBMS
3. Multi-Entity Customers, Orders, and Stock linked together → DBMS
4. Security Row-level security, ACID compliance, audit trails → DBMS

8.1.4 Database Locations & Access Models

💻

1. Local / Desktop Database

Resides entirely on the local computer's primary storage (SSD/HDD). The database engine and application run on the same workstation.

Examples: Microsoft Access (.accdb), SQLite, embedded mobile app databases.
Use Case: Single user / offline
🏢

2. Network / On-Premises Server

Hosted on a dedicated central server within the organisation's Local Area Network (LAN). Client workstations connect over the network.

Examples: Internal Microsoft SQL Server, on-prem PostgreSQL, Oracle database.
Use Case: Office LAN / High security
☁️

3. Cloud-Hosted Database (DBaaS)

Hosted in high-availability cloud data centres. Managed by cloud providers with automated geo-replication, backups, and elastic scaling.

Examples: AWS RDS, Azure SQL Database, Google Cloud Spanner, Snowflake.
Use Case: Web apps / Global scale
Topic 8.2 • Data Classification, RDBMS vs NoSQL & Document Stores

8.2 Database Structures & Non-Relational Types

Understand how enterprise data is structured and stored across different database architectures. Contrast structured relational tables against flexible semi-structured JSON documents and high-speed key-value stores.

8.2.1 The Data Classification Spectrum

CompTIA Tech+ 9.2.1 • Slides 20–21
📊 Structured Data RDBMS

Data that conforms to a rigid, pre-defined schema. Organised strictly into two-dimensional tables with designated fields and records. Every field adheres strictly to its declared data type.

Vocational Examples: • Bank account ledgers (SortCode, Balance) • NHS patient register (NHS_Number, DOB) • SQL inventory tables
📑 Semi-Structured Data JSON / XML

Data that does not fit into a rigid table grid, but contains self-describing tags, markers, or hierarchical keys that separate elements and define field hierarchies.

Vocational Examples: • JSON API payloads for web services • XML invoice and shipping documents • NoSQL document store records
🎥 Unstructured Data Raw Media

Data that has no conceptual schema or internal tags whatsoever. Represents over 80% of all data created in modern enterprises. Stored as raw binary objects or blob files.

Vocational Examples: • CCTV security video recordings (.mp4) • Doctor audio dictation recordings (.wav) • Scanned handwritten paper receipts (.pdf)
📮

Everyday Analogy: The Postal & Parcel Delivery Spectrum

Mental Model

To easily remember how data classification works in real-world IT and exams, compare the three types to everyday postal communications:

1. Structured Data Rigid Grid
A UK Passport Application Form

Think of the pre-printed paper form with individual square boxes. You are strictly required to write exactly one capital letter per box. If you try to write a sentence across three boxes or draw outside the margins, the Passport Office scanner rejects it instantly.

Database Match: Relational SQL table with strict column types and fixed character limits.
2. Semi-Structured Data Tagged Package
An Amazon Delivery Parcel

The contents inside the cardboard box can be wildly different — a pair of trainers, a heavy book, or a fragile glass mug. However, on the outside is a standardized key-value shipping label (Recipient, Postcode, Tracking ID, Weight). Couriers scan the label keys without needing to unbox the item.

Database Match: JSON or XML files and NoSQL document stores with flexible content but explicit tags.
3. Unstructured Data Raw Content
A Handwritten Letter or CCTV Video

A personal handwritten note, an MP3 voicemail, or a 1080p CCTV camera feed. It contains massive amounts of valuable information, but there are no internal grid lines, key-value labels, or predefined fields. A computer cannot automatically query "row 4, column 2" without running artificial intelligence or manual human review.

Database Match: Cloud Object Storage (e.g. AWS S3, Azure Blob) storing raw binary files.

8.2.3 Relational (RDBMS) vs. Non-Relational (NoSQL) Databases

CompTIA Tech+ 9.2.2 • Slide 22
Architectural Property Relational DBMS (RDBMS / SQL) Non-Relational (NoSQL) Best Vocational Choice
Data Model Rigid tables with pre-defined schema, fields, and records. Dynamic documents (JSON), key-value pairs, or graphs. RDBMS for strict accounting; NoSQL for variable catalog specs.
Query Language Standard Structured Query Language (SQL). Varies by engine (UnQL, MongoDB query syntax, JSON APIs). SQL is the universal industry standard language.
Scalability Model Vertical scaling (Scale Up: add more CPU and RAM to one main server). Horizontal scaling (Scale Out: distribute shards across dozens of commodity servers). NoSQL for massive web clickstream data across clusters.
Data Integrity Guarantees ACID Compliant: Atomic, Consistent, Isolated, Durable transactions. BASE Model: Basically Available, Soft state, Eventual consistency. RDBMS for financial transactions where money must balance.

8.2.4 Key-Value Databases: The In-Memory Speed Engine

CompTIA Tech+ 9.2.3 • Slide 24
Sub-Millisecond Speed (O(1))

The simplest and fastest NoSQL model. Every data record consists strictly of a unique Key linked to an arbitrary Value. Because data is held directly in system RAM and addressed by key hash, lookup time is constant O(1) — delivering retrieval in under 1 millisecond.

8.2.5 Document Databases: Dynamic Schema Inspector

CompTIA Tech+ 9.2.4 • Slide 25
Polymorphic JSON Storage

Document databases store records as self-contained, nested documents (typically JSON / BSON). Unlike relational tables which enforce identical column structures across every row, document stores are polymorphic: each item stores only the attributes it actually possesses.

Vocational Engines & Use Cases: MongoDB, Amazon DocumentDB, Google Cloud Firestore. Standard for e-commerce catalogues, user profiles, mobile apps, and gaming inventories where items have diverse attributes.
Topic 8.3 • Schemas, Tables, Keys & Referential Integrity

8.3 Relational Databases & Schema Design

Master the foundational building blocks of relational database architecture. Learn how tables, records, and fields model real-world business entities, enforce strict data types, and link data across tables using Primary and Foreign Keys without data anomalies.

8.3.1 Relational Schema Architecture: The Master Blueprint

CompTIA Tech+ 9.3.1 • Slide 29

In a relational database, the schema is the formal structural blueprint that defines the organisation, relationships, constraints, and data types of every element before any records are entered. Just as an architect drafts building blueprints before bricklayers pour concrete, a database administrator designs the schema before applications begin inserting records.

1. Structural Invariants: Defines table names, permitted column fields, and allowed data types.
2. Integrity Constraints: Enforces unique Primary Keys, non-null requirements, and valid foreign key links.
3. Access Policies: Specifies role-based access permissions and security boundaries per table.
📐

Deep Dive Analogy: The Building Blueprint & Regulations Inspector

Mental Model

To understand why databases require a strict schema before any data is entered, imagine constructing a modern hospital or apartment block:

ROOMS = TABLES

The architect designates specific rooms (Kitchen, Ward, Pharmacy). You cannot place patient beds in a room that hasn't been built.

PIPES & WIRES = DATA TYPES

Plumbing and 240V wiring are pre-sized. You cannot plug an electric toaster into a water pipe — just as you cannot insert text into an integer field.

DOOR NUMBERS = PRIMARY KEYS

Every room has a unique door number (Flat 101, Flat 102). No two rooms can have the same number, ensuring mail is never misdelivered.

HALLWAYS = FOREIGN KEYS

Corridors safely link rooms together. The blueprint strictly forbids building a doorway opening out into mid-air without a destination room (orphan record)!

The Building Inspector (DBMS Engine): Just as a city building inspector checks the construction site and halts illegal work, the DBMS software engine intercepts every query and rejects anything that violates the architectural schema.

8.3.2 Tables, Records & Fields (Slide 30 & CompTIA Tech+ 9.3.2)

🗂️ Table (Entity)

Container

A discrete collection of related data regarding a single real-world business entity (e.g. tbl_customers, tbl_orders, tbl_inventory).

📄 Record (Row / Tuple)

Horizontal

A single complete horizontal instance of data across all columns (e.g. Row #101 containing Customer "Dr. Patel", telephone number, and hospital clinic address).

📊 Field (Column / Attribute)

Vertical

A vertical category holding a specific property of every record. Every field is restricted to a single defined data type (e.g. price_gbp must be DECIMAL).

🏫

Everyday Metaphor: The School Class Register & Gradebook

Mental Model

To never mix up Tables, Records, and Fields in exams or on the job, picture a traditional teacher's paper class register or gradebook binder:

THE TABLE The Entire Entity
The Class Register Binder

The physical binder on the teacher's desk labeled "GCSE Computer Science — Year 10". It holds all attendance and grade information for one distinct group of people. In a database, this is tbl_students.

THE RECORD (ROW) Horizontal Slice
One Student's Complete Line

Look horizontally across line 14: "Liam Smith • Mon: Present • Tue: Present • Wed: Late • Exam: 84%". Reading horizontally tells you the complete story of ONE individual person.

THE FIELD (COLUMN) Vertical Slice
Friday Morning's Column

Look vertically down the column labeled "Friday AM Attendance". Scanning vertically tells you ONE single attribute across EVERY student in the class.

🎯 The Golden Exam Rule: Horizontal (Row) = One person's entire profile • Vertical (Column) = One single property across all people.

8.3.4 Primary Keys (PK)

CompTIA Tech+ 9.3.3 • Slide 31
Unique • Non-Null

A field (or set of fields) that uniquely identifies every individual record in a table. No two records can share the same Primary Key.

3 Strict Primary Key Rules:
  • Must be Unique: Duplicate values are rejected immediately by the DBMS.
  • Cannot be NULL: Every record MUST possess a valid identifier.
  • Immutable: Values should not change over time (e.g. Student ID, NHS No).
🪪 Everyday Analogy: The College Student ID Lanyard

Think of the ID number printed on your college badge (e.g. STU-9942). Even if two students in your cohort are both named "Alex Taylor" and share the exact same birthday, their Student IDs are strictly distinct. The college database uses this as the Primary Key so bursaries and exam grades are never mixed up.

🔗

8.3.5 Foreign Keys & Referential Integrity

CompTIA Tech+ 9.3.3 • Slide 31
Relational Glue

A field in a child table that refers directly to the Primary Key of another parent table, creating a formal relational link between records.

Referential Integrity Protection:

The database engine actively blocks you from entering an order with a customer_id that does not exist in tbl_customers! This prevents "orphan records" from corrupting business data.

📚 Everyday Analogy: The Library Book Checkout Slip

When you borrow a textbook from the campus library, the system creates a loan record in tbl_book_loans. Next to the book barcode, the librarian scans your Student ID (STU-9942) as a Foreign Key. The loan slip doesn't duplicate your home address or phone number — it simply points back to your master record.

Integrity Lock: The scanner rejects the checkout if the Student ID does not exist, and the college system blocks withdrawing while unreturned loans exist (ON DELETE RESTRICT).
🪜

Visual Schema Flow: Parent Table → Linking Table → Child Items

1-to-Many Relational Hierarchy

Level 1 learners often struggle to see how separate tables join together without duplicating data. Follow this 3-tier cascade showing how an enterprise e-commerce system links customer records down to individual hardware components:

1. PARENT TABLE tbl_customers
CustomerID [PK]: 101
FullName: Dr. Aris Thorne
Email: aris@techplus.ac.uk

Stores the customer identity once. CustomerID is the immutable Primary Key.

2. LINKING TABLE tbl_orders
OrderID [PK]: 5001
CustomerID [FK]: 101 ← (Refers to Parent)
OrderDate: 2026-11-26
Status: Dispatched

Contains order metadata. Foreign Key CustomerID = 101 ties this purchase to Dr. Thorne.

3. CHILD ITEMS TABLE tbl_order_items
LineID [PK]: 9210
OrderID [FK]: 5001 ← (Refers to Order)
PartNumber [FK]: RAM-DDR5-32
Quantity: 2 • UnitPrice: £119.99

Stores the physical items. Two Foreign Keys link back to the Order and the Component Inventory.

🛡️ The 3 Inviolable Vocational Invariants for Relational Databases
1. The Primary Key Invariant

Every table MUST have one Primary Key. It must be 100% unique, non-null, and immutable. An auto-increment integer (INT AUTO_INCREMENT) is the industry standard.

2. The Foreign Key Invariant

Any value stored in a child Foreign Key field MUST already exist as a Primary Key in the parent table. Entering an unknown ID triggers an instant constraint rejection.

3. Referential Integrity Lock

The DBMS actively forbids deleting a parent record (e.g. Customer 101) while active orders still refer to it. This prevents ghost or orphan orders in billing and shipping.

Topic 8.4 • Industry Roles, Responsibilities & Certifications

8.4 Careers in Databases & Systems Administration

Explore the high-demand vocational pathways in database management and analytics. Understand the distinct day-to-day responsibilities, toolsets, and professional certification roadmaps for Database Administrators, Data Analysts, and Database Developers.

🛡️ Infrastructure & Security

Database Administrator (DBA)

Slide 34 • CompTIA Tech+ 9.4

The guardian of the organisation's central data assets. Responsible for ensuring database servers run with 99.999% uptime, data is securely backed up, and access is strictly audited.

Core Daily Duties:
  • Configuring daily automated backups & recovery drills
  • Managing Role-Based Access Control (RBAC) & passwords
  • Monitoring server CPU, memory, and disk I/O performance
  • Applying security patches and operating system updates
Core Tools: SQL Server Mgmt Studio (SSMS), pgAdmin, Linux CLI
UK Salary Range: £35,000 – £65,000+
📈 Business Intelligence

Data Analyst

Slide 34 • CompTIA Tech+ 9.4

The analytical storyteller who translates raw database numbers into strategic business insights for directors, managers, and operational teams.

Core Daily Duties:
  • Authoring complex SQL queries (SELECT, JOIN, GROUP BY)
  • Building interactive live dashboards in PowerBI & Tableau
  • Cleaning corrupted or duplicate customer survey records
  • Spotting seasonal customer purchasing and revenue trends
Core Tools: SQL, Microsoft PowerBI, Tableau, Excel, Python
UK Salary Range: £28,000 – £52,000+
⚙️ Architecture & Code

Database Developer / Data Engineer

Slide 34 • CompTIA Tech+ 9.4

The software engineer who architects the underlying relational schemas, writes stored procedures, and constructs automated ETL data delivery pipelines.

Core Daily Duties:
  • Designing normalised schemas, tables, and foreign keys
  • Writing database triggers, stored procedures, and views
  • Building ETL (Extract, Transform, Load) data pipelines
  • Migrating on-premises SQL databases into cloud services
Core Tools: T-SQL, PL/SQL, Python, Snowflake, AWS Glue
UK Salary Range: £38,000 – £70,000+

💼 Technician Top Tips for Junior Database & Support Job Applications
1. Build a Public SQL Portfolio

Don't just write "SQL" on your CV. Create a free GitHub repository containing 3 cleanly commented SQL scripts that query real UK open data (e.g. ONS census or TfL transport data) using WHERE, GROUP BY, and ORDER BY.

2. Master the #1 Interview Question

Almost every junior entry interview asks: "Can you explain Primary Keys vs Foreign Keys to a non-technical manager?" Always explain the Customers and Orders analogy — it proves you understand referential integrity.

3. Target UK Entry-Level Titles

Search for: Junior Application Support Analyst, First-Line Data Operations Technician, or IT Systems Coordinator. UK entry salaries range from £24,000 – £30,000.

Lesson 8 Plenary: What We Have Learnt Today

Slide 37 Summary
1. Database vs. Spreadsheet:

Spreadsheets suffer file lock collisions and redundancy; relational databases deliver multi-user row-level concurrency, granular security, and ACID compliance.

2. Data Classifications:

Structured data lives in rigid tables (SQL); semi-structured data uses self-describing tags (JSON/XML/NoSQL); unstructured data represents raw media files.

3. Primary & Foreign Keys:

A Primary Key uniquely identifies a single record. A Foreign Key points to a Primary Key in another table, enforcing referential integrity and eliminating orphaned records.

4. Practical SQL Commands:

Standard SQL executes SELECT (retrieve), WHERE (filter), ORDER BY (sort), INSERT (add), UPDATE (change), and DELETE (remove) across relational tables.
